Mini Threat Intelligence PlatformA Python-based threat intelligence and SOC investigation platform that automates IOC analysis, reputation checking, risk scoring, alert prioritisation, threat intelligence enrichment, investigation tracking, SOC reporting, and dashboard visualisation.This project was developed as a personal cybersecurity portfolio project to demonstrate practical threat intelligence, SOC analysis, Python development, API integration, security automation, and investigation workflow skills.\------------------------------------------------------------------------------------------------------------------------------------------------------------**1. Project Overview**The Mini Threat Intelligence Platform processes Indicators of Compromise (IOCs) such as IP addresses, domains, URLs, and file hashes through multiple threat intelligence and security analysis stages.The platform combines automated threat intelligence sources with risk scoring, alert prioritisation, enrichment, investigation tracking, reporting, and dashboard visualisation.Platform WorkflowIOC Input&#x20;   ↓IOC Analysis \& Normalisation&#x20;   ↓VirusTotal Reputation Check&#x20;   ↓Risk Scoring \& Threat Classification&#x20;   ↓Alert Prioritisation&#x20;   ↓Alert Filtering&#x20;   ↓AbuseIPDB + AlienVault OTX Enrichment&#x20;   ↓Investigation Workflow&#x20;   ↓Investigation Summary&#x20;   ↓Investigation Report&#x20;   ↓SOC Reporting&#x20;   ↓CSV / TXT Persistence&#x20;   ↓Streamlit SOC Dashboard\------------------------------------------------------------------------------------------------------------------------------------------------------------**2. Objectives**The main objectives of this project are to:* Analyse and classify different types of IOCs.* Automate IOC reputation checking using threat intelligence APIs.* Calculate a risk score based on threat detection results.* Classify IOCs according to their risk level.* Prioritise alerts based on risk severity.* Filter alerts for investigation.* Enrich IOC information using additional threat intelligence sources.* Support an investigation workflow for security analysts.* Generate structured SOC investigation reports.* Persist investigation data using CSV files.* Provide a visual SOC dashboard for monitoring and investigation.* Demonstrate practical cybersecurity and SOC analyst skills.\------------------------------------------------------------------------------------------------------------------------------------------------------------**3. Risk Scoring Methodology**The risk scoring system converts IOC detection results into a numerical score.The methodology considers the proportion of malicious and suspicious detections reported by available security engines.The current scoring model gives significantly greater weight to malicious detections than suspicious detections.Risk Classification0 ───────────────────────────────────── 100LOW          MEDIUM        HIGH        CRITICAL0–19         20–39         40–69       70–100An IOC with no available reputation information is classified as UNKNOWN and requires manual review.ExampleExample malicious IOC:Malicious detections: 66Total engines:        74Detection ratio:      89.19%Risk level:           CRITICAL\------------------------------------------------------------------------------------------------------------------------------------------------------------**8. Alert Prioritisation**The alert prioritisation system converts risk classifications into SOC-style priorities.CRITICAL  → P1HIGH      → P2MEDIUM    → P3LOW       → P4UNKNOWN   → P4This provides a structured way to focus investigation attention on higher-risk indicators.\------------------------------------------------------------------------------------------------------------------------------------------------------------**9. Configuration**The platform uses environment variables to securely store API keys required by external threat intelligence services.Create a .env file in the project root:VIRUSTOTAL\_API\_KEY=your\_virustotal\_api\_keyABUSEIPDB\_API\_KEY=your\_abuseipdb\_api\_keyOTX\_API\_KEY=your\_otx\_api\_keyAPI Key UsageEnvironment Variable	Service	PurposeVIRUSTOTAL\_API\_KEY	VirusTotal	IOC reputation and detection informationABUSEIPDB\_API\_KEY	AbuseIPDB	IP abuse and network informationOTX\_API\_KEY	AlienVault OTX	Threat intelligence enrichmentThe application loads these values using python-dotenv.SecurityAPI keys should never be hard-coded into Python source files or committed to a public repository.The .env file is excluded from Git tracking through .gitignore:.env\_\_pycache\_\_/Never place real API keys in the README or any public source file.\------------------------------------------------------------------------------------------------------------------------------------------------------------**14. Limitations**API Dependency* The platform depends on external threat intelligence APIs. API availability, rate limits, quotas, and response changes can affect the results.IOC Coverage* Not every IOC type is supported by every enrichment source.* For example, AbuseIPDB primarily provides information for IP addresses, while other sources may provide different types of intelligence.CSV Storage* The current platform uses CSV files for persistence.* This is suitable for a small portfolio project but would not be ideal for a large production SOC environment with many analysts and concurrent investigations.Risk Scoring* The risk scoring methodology is a simplified model designed for this project.* Real SOC environments may use more complex scoring models that consider asset criticality, threat context, confidence, campaign information, historical activity, and organisational risk.No Live SIEM Integration* The platform currently operates as a standalone threat intelligence and investigation platform and does not directly ingest alerts from enterprise SIEM platforms.\------------------------------------------------------------------------------------------------------------------------------------------------------------**18.
